# 风险登记表

为了保证「小概率匹配平台 (主线)」在执行生产冒烟测试和后续持续迭代中的高可用与安全性，在此记录项目已识别的核心技术与业务风险，并制定针对性的缓解措施与日常排查规范。

---

## ⚠️ 1. 环境变量缺失风险

*   **严重级别**：高 (High)
*   **触发条件**：
    *   在本地、测试（Staging）环境开发了微信支付、短信验证、百度统计/推送或 JWT 等新功能，但未能在 Vercel 生产（Production）后台同步新增对应的环境变量。
    *   配置部署时未区分开发环境凭证与生产环境凭证，或填入的字符包含隐藏的多余空格。
*   **影响**：
    *   用户在生产环境无法收到短信验证码、无法发起支付充值、无法完成微信快捷登录，从而导致核心业务流全线瘫痪。
    *   接口报错 `500 Internal Server Error`，造成极坏的用户体验与负面口碑。
*   **缓解措施**：
    *   **环境变量校验分级隔离原则**：
        *   **核心启动变量**（如 `SUPABASE_URL`、`SUPABASE_ANON_KEY`）：这是平台最底层的基础配置。若缺失将导致所有数据库交互失败，允许在 Web 服务启动阶段校验并直接抛出错误阻断应用启动。
        *   **服务端关键变量**（如 `SUPABASE_SERVICE_KEY`）：仅当涉及到特权服务端的逻辑时需要。若缺失，相关特权 API 应返回清晰、可识别的错误，同时应在 CI/CD 部署流水线及发布 Checklist 的检查环节进行拦截，阻断上线，但不得直接导致应用进程崩塌。
        *   **功能型变量**（如 `JWT_SECRET`、`IP_HASH_SECRET`、`WECHAT_API_KEY`、`TENCENT_SECRET_KEY`、`BAIDU_PUSH_TOKEN` 等）：这类变量仅服务于局部独立功能。**严禁在启动阶段因为功能型变量缺失而直接阻断服务启动，或使非相关的公共页面抛出 500 错误**。一旦缺失，必须采用局部降级与禁用逻辑：
            *   `JWT_SECRET` 缺失：仅影响需要 JWT 校验的管理后台（admin）登录与接口鉴权，绝对不能影响主站公开首页。
            *   `IP_HASH_SECRET` 缺失：仅导致 `/api/track` 埋点接口上报失败（可打出 error 日志并降级兜底），绝对不能导致公开的 SSR 页面无法渲染。
            *   `WECHAT_API_KEY` 缺失：仅在用户拉起微信支付下单时进行拦截，返回“支付功能维护中”，绝对不能阻断游客浏览公开项目或开发者列表。
            *   `TENCENT_SECRET_KEY` 缺失：仅导致短信发送失败，不能导致非登录态游客浏览时报 500。
            *   `BAIDU_PUSH_TOKEN` 缺失：仅在发布内容时无法向百度推送 URL，不应影响任何用户端的正常交互。
    *   **架构解耦原则（禁止公共页面加载路径 import 顶层 throw 的功能模块）**：
        *   在编写公共页面（如 `/`、`/projects`、`/developers` 等 SSR 页面）以及公开 API 的代码时，必须确保其依赖的底层工具包在 import 时是干净的。
        *   任何在顶层（Top-level scope）读取环境变量并可能直接 throw error 的模块（如初始化某 SDK 并对 key 做强校验的模块，如 admin-auth），绝对不应在公共页面或公开 API 的加载依赖链中被顶层引入。这类抛错模块的加载应限定在需要使用的特定 API/函数内部，或者通过惰性初始化（Lazy Initialization / Dynamic Import）延迟载入，物理限制故障扩散半径。
    *   **配置规范化**：严格维护 `mirauni-frontend/.env.example` 和 `mirauni_app/lib/config/env.dart`。任何新加环境变量的任务必须在 implementation plan 中显式声明。
*   **检查方式**：
    *   在 Vercel 每次重新发布后，运行生产环境健康检查脚本，或手动执行登录与模拟支付流程。
    *   在命令行运行 `git status` 确认没有将本地 `.env` 提交到 Git 历史。

## ⚠️ 2. Supabase Migration 风险

*   **严重级别**：最高 (Critical)
*   **触发条件**：
    *   对生产数据库直接进行 DDL 修改而不经过 SQL 脚本迁移，或者在 `supabase/migrations/` 中编写了不向下兼容的改动（例如删除正在被生产代码引用的字段、更改数据类型、增加无默认值的 `NOT NULL` 字段等）。
*   **影响**：
    *   导致当前运行的生产 API 突然崩溃，或者引发触发器（Trigger）失效。
    *   导致用户数据受损、丢失或脏数据混入，系统无法回滚。
*   **缓解措施**：
    *   遵循“向前兼容两步走”原则：如果需要重构字段，第一步先新增字段并做好代码兼容，保证老代码读写新列；第二步等新版代码完全稳定投产后，再通过新迁移将旧列删除。
    *   严禁对线上数据库直接进行破坏性手工更改，所有 Schema 变更必须在测试环境运行 `supabase db push` 进行仿真预演。
*   **检查方式**：
    *   在应用迁移后，执行 `supabase db lint` 检查 SQL 是否有效。
    *   确认生产部署前已自动或手动执行 Supabase 控制台的数据库快照备份。

## ⚠️ 3. RLS 规则误伤业务风险

*   **严重级别**：高 (High)
*   **触发条件**：
    *   在 Supabase 控制台中过度收紧 Row Level Security (RLS) 策略，或者在 SQL 中编写了错误的 `USING` / `WITH CHECK` 逻辑（例如对关联表的判定中未使用主键，或对匿名角色的 SELECT 规则有误）。
*   **影响**：
    *   合法的前端用户在进行项目检索、开发者详情查询、个人站内信发送或执行解锁扣费（`unlock_user_contact` RPC）时，遭到数据库拦截，返回 `403 Forbidden` 或空数据集。
*   **缓解措施**：
    *   对所有包含 RLS 改动的迁移脚本编写针对性的单元测试。
    *   将敏感数据的交互（如扣费、查看解锁后的隐私字段）封锁在服务端安全边界内，由 RPC (Service Role) 统一处理。
*   **检查方式**：
    *   部署后以不同身份登录（游客、新注册用户、已付费用户、管理员），针对 `projects`、`public_profiles`、`unlocks` 表进行读写冒烟，确认返回的状态码和数据集符合预期。

## ⚠️ 4. AI 并行开发冲突风险

*   **严重级别**：中 (Medium)
*   **触发条件**：
    *   在仓库中，多个 AI 助手（如 research、governance 代理等）同时对代码、配置进行修改；或者由于 AI 未及时拉取远端最新分支，导致在合并时产生大面积的代码冲突。
*   **影响**：
    *   代码被旧版本覆盖，已修复的漏洞发生 Regression（回归）；代码逻辑不一致导致编译失败；开发进度被阻碍。
*   **事实来源修正**：
    *   **以 main 分支代码、Supabase migrations、生产配置、CI 状态和 PR 状态作为事实来源**。
    *   `docs/progress.md` 仅作为进度跟踪文档，必须随实际状态更新，**不得凌驾于真实代码和生产状态**。
*   **缓解措施**：
    *   AI 在每次启动任务前，必须拉取最新的 `main` 并在本地执行 `git pull` 与类型校验。
    *   在完成任何阶段性改动后，AI 必须严格执行完校验并更新进度，然后向用户提交说明。保持分支粒度细小，避免使用生命周期过长的分支。
*   **检查方式**：
    *   在执行发布前，使用 `git diff main...` 仔细对照变更清单。

## ⚠️ 5. 支付配置缺失风险

*   **严重级别**：高 (High)
*   **触发条件**：
    *   项目上线生产后，未配置真实的微信商户号（`WECHAT_MCH_ID`）、微信支付 API 密钥（`WECHAT_API_KEY`）及微信证书，或者配置的值与微信商户平台后台不一致；微信支付回调通知 URL（`/api/payment/notify`）未配置白名单。
*   **影响**：
    *   用户在充值页面发起支付时遭遇“订单初始化失败”或“签名无效”错误，无法调用微信支付；
    *   用户支付成功后，微信回调系统无法通知到平台，导致订单一直处于“待支付”，用户额度无法增加，引起客诉。
*   **缓解措施**：
    *   在 Staging 环境建立完整的沙箱模拟微信支付接口与回调对账系统，确保底层支付回调签名算法完全正确。
    *   上线后，首先执行一次“一分钱真实充值测试”并解锁联系人，确保整条资金链畅通。
*   **检查方式**：
    *   检查 Vercel Functions 运行日志，查看接口 `/api/payment/create-order` 与 `/api/payment/notify` 的响应码及参数。

## ⚠️ 6. SEO 改造引入 404 风险

*   **严重级别**：中 (Medium)
*   **触发条件**：
    *   将旧的基于纯数值或 UUID 的路由跳转（如 `/projects/[id]`）改为新的语义化 Slug 路由（如 `/projects/[slug]`），但未在服务端设置兼容转换层，导致已被搜索引擎收录的历史页面瞬间失效。
*   **影响**：
    *   搜索引擎抓取错误率飙升，导致整站权重被下调，搜索引擎流量雪崩；
    *   外部博客或媒体分享的旧页面链接全部报 404。
*   **缓解措施**：
    *   在 Nuxt 3 路由拦截器或 Server 中间件中配置 301 重定向逻辑：若匹配到旧格式的参数（如纯数字或 UUID），则通过底层数据库反查对应的 Slug 字段，并将客户端以 301 永久重定向（`Redirect Permanent`）的方式重定向到最新的 Slug 页面。
*   **检查方式**：
    *   使用旧的物理 URL 进行请求，验证 Response Header 中是否包含 `Status Code: 301 Moved Permanently` 并且 `Location` 准确指向新 URL。

## ⚠️ 7. Vercel Preview 被误认为 Production 的风险

*   **严重级别**：高 (High)
*   **触发条件**：
    *   AI 或开发者直接在 PR 的 Vercel Preview（预览）部署页面中进行了写操作，或者预览环境被配置了与生产完全相同的敏感 API key、Supabase 生产数据库密钥，并且没有进行环境级别的来源防御。
*   **影响**：
    *   在测试 Preview 分支的功能时，误对生产数据库插入了垃圾测试数据或修改了线上真实用户的付费状态，严重污染生产数据。
    *   在预览中发起的测试支付误扣款，或触发了生产环境的回调通知。
*   **缓解措施**：
    *   在 Vercel 环境变量配置中，严格区分为 `Production`、`Preview` 和 `Development` 三种环境的变量值，使用完全隔离的 Supabase Staging 数据库。
    *   在关键的安全写接口和微信回调验证中，检测当前域名，若非 `mirauni.com` 则禁止写入生产存储。
*   **检查方式**：
    *   确认 Preview 部署下，其控制台环境变量中的 `SUPABASE_URL` 和 `SUPABASE_ANON_KEY` 分别指向开发/测试项目的实例。

## ⚠️ 8. Secret 泄露风险

*   **严重级别**：最高 (Critical)
*   **触发条件**：
    *   开发者或 AI 助手在提交代码、排查报错或编写调试脚本（如 `scratch/`）时，误将包含 `JWT_SECRET`、`SUPABASE_SERVICE_KEY`、微信支付私钥或腾讯云短信 API Key 的明文直接写入到提交文件、注释、甚至是公开的测试接口中并推送到 GitHub。
*   **影响**：
    *   黑客通过自动化扫描爬取 GitHub 泄露的密钥，利用 Service Role 权限直接接管并清空 Supabase 数据库，窃取全量用户信息，或者恶意盗刷腾讯云短信、盗领微信商户余额。
*   **缓解措施**：
    *   在 `.gitignore` 中配置彻底屏蔽 `.env`、`config/env.dart` 敏感配置文件，以及 `scratch/` 目录。
    *   在项目中集成密钥扫描工具（如 GitLeaks 或 GitHub Advanced Security Secret Scanning）。
*   **检查方式**：
    *   执行 `git diff` 仔细逐行查看提交的内容。
    *   若发生泄露，必须立刻在云平台吊销并重新生成所有泄露的密钥。
